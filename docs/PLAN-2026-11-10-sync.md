## Design

**Files (R1, R4, R5, R9).** One clone per distinct (normalised remote, ssh_key) at `$LESSONS_HOME/sync/<remote slug>/`, holding one
`<domain>.jsonl` per domain synced through it, and `<domain>.conflicts.jsonl` while that domain has queued conflicts. No `.gitattributes`,
no merge driver. The live DB stays at `$LESSONS_HOME/<domain>.db` (unchanged layout; `db::Domain::file_path`). Beside the clone, per
remote slug: `<slug>.lock`, `<slug>.state` (last pull time, consecutive failures, last access check, `last_synced_commit`),
and the LIVE queue `<slug>.<domain>.conflicts.jsonl`. The live queue is outside the clone on purpose (R9): step 6 resets
the clone with `checkout -f`, which would undo a queue edit made by `lessons resolve`. The committed copy in the clone is written from the
live one by the cycle.

**Constants (R3, R6, R7, R9)**: `ACCESS_RECHECK_DAYS`, `PUSH_ATTEMPTS`, `BACKOFF_CAP_MINUTES`, `SYNC_FALLBACK_BRANCH = "main"` (empty remote
only), `NEEDS_REWORD_TAG = "needs-reword"`; each is a named `const`, none shared with unrelated code.

**Config (R2, R5)** (`src/config.rs`, `Config` gains `sync: SyncSection`):

```toml
[sync.shared]
remote = "git@github.com:HidekiAI/lessons-data.git"   # R2, R5
ssh_key = "~/.ssh/id_ed25519_personal"      # R2, R6: private key, or a .pub whose private key an agent holds
update = "live"                             # R3: "live" | "on-demand"
pull_every_minutes = 10                     # R3: pull throttle for reads (both strategies)
```

`SyncSection { work, personal, shared: Option<SyncConfig> }` with `deny_unknown_fields` (R1, R2).
Remotes are compared after normalising (trailing `/` and `.git` removed, host case-folded). Domains with the same normalised
remote AND the same `ssh_key` share one clone with both domain files in it (R5). Same remote with DIFFERENT `ssh_key` for two domains on one
machine is a config load error (R5: one clone has one `core.sshCommand`). Same remote and same key for `work` and another domain
is allowed, with a stderr warning (R6): work data is readable by anyone who can read that repo, and the R6 probe has no second key to test.

**Key isolation (R2, R6, R7)**. Every git call that talks to a remote, probes included, uses
`ssh -i <key> -o IdentitiesOnly=yes -o BatchMode=yes` plus an option that stops `~/.ssh/config` `IdentityFile` entries from being added
(set as `core.sshCommand` in the clone, as `GIT_SSH_COMMAND` for probes; the probe's command also carries `-v`, below). `BatchMode=yes` is on EVERY
ssh invocation: OpenSSH reads `/dev/tty` directly for a key passphrase and for the host-key question, and `GIT_TERMINAL_PROMPT=0` does not cover ssh.
With it a prompt becomes a failure (`Inconclusive` for a probe, a sync failure counted for backoff), so sync never prompts (R3). The exact
isolation option is NOT asserted here: S1 verifies it
against `man ssh_config` on this host and by experiment, and records the verified choice in its result. Candidates: `-F /dev/null`
(also drops `IdentityAgent` from the user's config, which a 1Password-held key given as a `.pub` needs) or an `-o IdentityFile=none` style
option. A `.pub` key path relies on an agent that holds the private key. The agent socket is resolved once per cycle (`IdentityAgent` from the user's ssh config if set, else `SSH_AUTH_SOCK`) and passed explicitly as `-o IdentityAgent=<socket>` (so `-F /dev/null`, which drops the config's `IdentityAgent`, cannot make ssh use a different agent). S1 records the verified form.

**Access guards (R6, R7)** (`sync.rs`; after the lock (step 1 of the cycle), before the first fetch of a clone, then every
`ACCESS_RECHECK_DAYS` [a key or repo can change visibility later], recorded in the state file). Fail-closed: any guard that cannot reach
a verdict refuses the WHOLE clone for this cycle, logged with the reason. A refusal counts as a failure for the backoff counter (R3), but the
verdict is never cached as a pass: no check time is recorded, so the next allowed cycle probes again. Probe outcome is classified from the
`git ls-remote` exit status and stderr (for an ssh remote, the `ssh -v` lines in it) into `Readable`, `AuthDenied`, `Inconclusive`:
- `AuthDenied` means the host authenticated the caller and then refused access: stderr "Repository not found" (GitHub prints
  "ERROR: Repository not found." only after authentication), "access denied". For the anonymous HTTPS probe (no identity to authenticate)
  also "terminal prompts disabled", "could not read Username", "Authentication failed".
  Candidate no-access strings for hosts other than GitHub (UNVERIFIED, from memory of those hosts): GitLab "The project you were looking for
  could not be found or you don't have permission to view it"; Azure DevOps "TF401019: The Git repository with name or identifier ... does not
  exist or you do not have permissions for the operation you are attempting". They join the list only as S5 confirms them.
- SSH probe (R6): the probe runs as `GIT_SSH_COMMAND="ssh -v -i <key> -o IdentitiesOnly=yes -o BatchMode=yes ..."` with stderr captured, so the
  `-v` lines say how far authentication got with THIS key. There is no separate key check. Classification:
  - exit 0 -> `Readable` (the key can read).
  - "Offering public key" and no "Server accepts key" -> the server rejected the key -> `AuthDenied`. This is how a host where the non-work key
    is not registered (company GitLab, Azure DevOps) still reaches a verdict.
  - "Server accepts key" followed by a signing failure (the agent refused, e.g. "signing failed", "agent refused operation") -> `Inconclusive`
    (the key is held by a locked or unapproving agent; the host never judged it).
  - "Server accepts key" and then the host's no-access message (above, e.g. "Repository not found") -> `AuthDenied`.
  - No "Offering public key" at all (key file missing or unreadable, passphrase-protected key refused by BatchMode, "Host key verification
    failed"), or any transport error -> `Inconclusive`.
- `Inconclusive`: "Permission denied (publickey)" without "Offering public key" or after a signing failure (above), "Could not resolve hostname", "Connection refused",
  "Connection timed out", "Network is unreachable", and any other non-zero exit with an unrecognised message; never `AuthDenied`. S5 records the
  exact strings and `-v` lines observed by hand for EVERY configured host (a known private and a known public repo on each).
- R6 (domain `work`): first `git ls-remote <work remote>` with the WORK key must be `Readable`; otherwise the guard cannot judge:
  refuse and retry later. Then each configured key that differs from the work key must probe `AuthDenied`. `Readable` -> refuse
  `work` and name the key. `Inconclusive` -> refuse this cycle. Consequence: on GitHub a non-work key must be registered with the host to reach
  "Repository not found"; on a host where it is not registered, a key the server rejects outright ("Offering public key", no "Server accepts key")
  is `AuthDenied`; a key that cannot even be offered stays `Inconclusive` and `work` stays refused (fail-closed).
- R7 (every domain): derive `https://<host>/<path>` from the remote (scp-like `git@host:path` and `ssh://git@host/path` forms);
  when it cannot be derived (an ssh alias, a custom port), refuse. Anonymous `git ls-remote` with `GIT_TERMINAL_PROMPT=0`,
  `GIT_ASKPASS=` (empty) and `-c credential.helper=`: `Readable` -> public -> refuse; `AuthDenied` -> private, pass;
  `Inconclusive` -> refuse this cycle.
- (R6, R7) The decision is a pure function `decide_access(config, probe)` taking the probe as a function
  argument; tests drive it with stubs returning each class. `classify_probe(exit_ok, stderr)` is a second pure function with its own table test (the `-v` line patterns above included). The real probes are exercised by hand (recorded in S5).
- Limit (R6): only keys configured on this machine are probed; a non-work key that is not in this config is not checked.
- Limit (R7): visibility is re-checked every `ACCESS_RECHECK_DAYS`, so a repo made public later is caught at the next recheck, not instantly.

**JSON lines (R4, R9).** `store::Lesson` gains `Deserialize`. One `serde_json::to_string(&Lesson)` per line, sorted by `id`
(ULIDs sort by creation, so appends land at the end and diffs stay small). `updated_at` is `%Y-%m-%dT%H:%M:%SZ` (fixed width), so string
order is time order. Its resolution is one second (`store::update`), so `updated_at` is only a label and a tie-breaker (below), never the
test for "changed": changes are detected by comparing fields (R4, R9).

**Merge (R4, R9)**: pure `sync::merge_lessons(base, ours, theirs) -> (Vec<Lesson>, Vec<Conflict>)`, per id. MERGED FIELDS are every field
except `id`, `created_at`, `updated_at` and `hits`: `title`, `context`, `problem`, `root_cause`, `resolution`, `failed_tries`, `tags`,
`env_versions`, `superseded_by`.

| base | ours | theirs | result |
| --- | --- | --- | --- |
| any | present | present | per-field three-way (rules below); `hits = max(ours, theirs)`; `updated_at = max(ours.updated_at, theirs.updated_at)` |
| absent | present | absent | ours (added here) |
| absent | absent | present | theirs (added there) |
| present | present, unchanged | absent | drop (theirs deleted it) |
| present | present, changed | absent | ours (an edit beats a delete) |
| present | absent | present, unchanged | drop (ours deleted it) |
| present | absent | present, changed | theirs (an edit beats a delete) |
| any | absent | absent | drop |

Per-field rule for each merged field `f` when the id is on both sides: if `ours.f == theirs.f` -> that value; else if `ours.f == base.f`
-> `theirs.f`; else if `theirs.f == base.f` -> `ours.f`; else CONFLICT on `f`. With no base row (BASE empty or lacking the id), a
differing field is a conflict. `updated_at` is the max of the two, never "now": a "now" would make every cycle change the row and ping-pong
between machines. For a CONFLICT the DB gets a DEFAULT WINNER chosen by a side-independent order: the value from the side with the newer
`updated_at`; on a tie, the larger value as a string (`None` compares as the empty string). So search keeps working and every machine
computes the same row. The other value is queued (below), never discarded. A conflict on `superseded_by` takes the default winner and is
logged, but is NOT queued: `store::update` cannot set it and it is a machine-written pointer, not text (follow-up). "Changed" in the
one-side-only rows compares the merged fields, not `hits`.

What this fixes (R4, R9): the old rule "newer `updated_at` wins, tie larger line" let an edit with an older or equal timestamp lose to an
unchanged copy of the same lesson, silently. Now an edit beats an unchanged copy whatever the timestamps say, two edits to different fields
both survive, and a true conflict keeps one value in the DB and the other in the queue, so nothing is ever discarded silently.

Convergence in one sentence: every rule depends only on the unordered pair (`ours`, `theirs`) plus BASE, never on which side is "ours", so
every machine computes the same MERGED and the same queue entries. An empty BASE (first sync, lost or unreadable state) makes every one-sided
id "added" and every differing field a conflict, so the first sync is a union that deletes nothing (a deletion made while the state was lost
resurrects: accepted, never data loss).

**Conflict queue (R9)**: one GROUP per (lesson id, field), so three or more versions of one field never become pairs:
`Conflict { id, field, base: Option<String>, versions: Vec<{value, updated_at}> }`, one JSON line each. The versions are an UNORDERED set keyed
by `value`, stored sorted by `(value, updated_at)`; the group KEY is `(lesson id, field)`, identical on every machine. A new conflict on a field that
already has a group adds its value to that group instead of making a new entry. The DB's default winner for the field is computed over ALL versions
of the group by the same side-independent order as before (newest `updated_at`, tie larger string), but ONLY in a cycle where the per-field rule
reports a CONFLICT on that field; otherwise the per-field rule's result stands even while a group exists for the field (for example ours == base
and theirs changed: theirs wins, not the all-versions default).
TAGS COMPARISON: whenever `tags` values are compared for the add-a-version check below, the `needs-reword` token is
ignored (the space-split sets minus `NEEDS_REWORD_TAG` are compared), so a combine on another field of the same lesson, which appends that token in
the same patch, never adds a spurious version to an existing `tags` group.
Pure `sync::merge_queue(base, live, theirs, new_conflicts)` runs in TWO ordered phases: (1) the three-way over BASE, LIVE and THEIRS, for groups
present in BASE only: a group in BASE and missing on one side was resolved there -> dropped; present on both -> the UNION of the version sets (same
`value` on both sides keeps the larger `updated_at`); groups NOT in BASE (added on either side) are kept, unioned when on both. (2) THEN `new_conflicts`
(keys not yet merged, found by `merge_lessons` this cycle) are unioned in; the phase-1 drop never removes them. If a NEW group has the same key as a
BASE group that one side resolved, phase 1 has already removed the resolved group (old versions included), so the NEW versions start a fresh group
under that key: no generation counter is needed, because the removal comes first. A group removed by a resolve on one side that the other side
extended with an older queued version is removed on both; that version meets the resolved value in the next merge and, if they differ, is queued again
as a new group (nothing is lost silently). `base` on a collision: the larger serialized value (side-independent).
ONLY `lessons resolve` clears a group (R9), with one exception: a group whose lesson no longer exists (in MERGED) is cleared and logged. A local edit
never drops a group. After `merge_queue` (cycle step 5), for each group whose lesson is in MERGED: if the field's value in MERGED is not among the group's
versions (TAGS COMPARISON applies), that value is ADDED to the group as a new version with the row's `updated_at`. This covers a local `lessons update`
on a field with a pending group, and a crash between a `resolve` update and its group removal. It depends only on MERGED, which is the same on every machine, so every
machine computes the same group (symmetry). A sync default winner is always one of the versions, so it adds nothing.
Both the live file and the committed `<domain>.conflicts.jsonl` are written from the result (temp + rename); an empty queue removes the committed
file. It is committed in the same commit as `<domain>.jsonl`. Machine B recomputing the conflict machine A already queued yields the same group
key and the same values, so it dedupes (R9 d).

**Sync cycle (R1, R3, R4, R9)** (`lessons sync [--domain <d>]`, new `src/sync.rs`), per clone, all its domains together. No `git pull`, no
`git merge`: git only ever fast-forwards, because every commit is made on top of the fetched remote tip.
1. Lock FIRST: open `sync/<slug>.lock` (create) and `File::try_lock` (std, stable since 1.89). Held by another process -> exit 0; that exit
   counts as no failure. The OS releases the lock when the process dies, so there is no stale-lock logic (R3: a crashed sync cannot block
   sync forever). `lessons resolve` takes the same lock, but only around each apply, and does not retry (R9, R10).
2. Run the access guards when due; a refusal or an `Inconclusive` result stops the clone, adds one to the failure counter (backoff, R3) and is not
   cached as a pass (R6, R7).
3. BRANCH = the remote's default branch, parsed from `git ls-remote --symref <remote> HEAD` (`ref: refs/heads/<name>\tHEAD`; run with the key
   isolation command as `GIT_SSH_COMMAND`, before the clone exists); only when that prints nothing (an empty remote) fall back to
   `SYNC_FALLBACK_BRANCH`. A `trunk` default is therefore followed, never forced to `main` (R1, R3). First run: `git init -q -b <BRANCH> <clone>`
   (so the local branch name never depends on `init.defaultBranch`), `git remote add origin <remote>`. Every cycle, idempotently: `git config
   core.sshCommand "<key isolation command>"`, `git config commit.gpgsign false` (R2, R3, owner answer).
4. `git fetch -q origin` (an empty remote fetches nothing). TIP = `git rev-parse --verify -q refs/remotes/origin/<BRANCH>` (none if the remote is empty).
5. Per domain: THEIRS = `git show <TIP>:<domain>.jsonl` and its `.conflicts.jsonl` (empty if no TIP or no such file). BASE = the same two files at
   `last_synced_commit` from the state file. An unreadable `last_synced_commit` (object missing, history rewritten, clone recreated, or none) means an
   EMPTY BASE, which is a union: logged with the commit id and the git error, never a permanent error (R4, R9). In ONE `BEGIN IMMEDIATE` transaction on
   `<domain>.db` (`store::all_lessons` then `store::apply_merged`): OURS = `all_lessons`; `(MERGED, NEW) = merge_lessons(BASE, OURS, THEIRS)`;
   QUEUE = `merge_queue(BASE queue, live queue, THEIRS queue, NEW)`, then clear groups of lessons absent from MERGED and add a version for each
   field whose MERGED value is not among its group's versions (see Conflict queue);
   apply MERGED minus OURS (insert, update, delete) in the same transaction; write the live queue (temp + rename) BEFORE committing the
   transaction; then commit. A crash between the queue write and the commit rolls the DB back, leaving a queue group whose losing value is still in
   the DB: harmless, the group key dedupes it, and `lessons resolve` sees the DB equal to one version and handles it normally. The reverse order would
   lose the losing value on a crash after the commit. Every other writer (`add`, `update`, `hit`, `retire`, `move`, MCP) waits on `busy_timeout` (5 s, `db::open`), so a
   local write can neither slip between the read and the apply nor be undone by it; a write that lands after this transaction is already in the DB and the
   next sync picks it up (R10).
6. Reset the clone to the remote tip: with TIP, `git checkout -q -f -B <BRANCH> <TIP>` (drops any file left uncommitted by a crash). Without TIP
   (an empty remote) run `git checkout -q -B <BRANCH>` (S4 verifies it on an unborn branch; it keeps any local commit): after a crash on an empty
   remote a local commit can already exist from an earlier cycle, and the next commit simply goes on top of it, so the push still fast-forwards the
   empty remote; if there is no local commit the branch is unborn and the commit is its first. Write each MERGED to `<domain>.jsonl` sorted by id and each non-empty QUEUE to `<domain>.conflicts.jsonl` (temp file +
   rename). Stage with `git add -f -A -- <those files>`: `-f` because a data repo set up per the old README FAQ carries a whitelist `.gitignore` (`*`,
   `!.gitignore`, `!shared.db`) that would otherwise ignore them, so such a repo syncs without edits (R1, R5). If `git diff --cached --quiet` reports a
   difference, `git commit -q -m "sync <domain list>"`.
7. If a commit was made: `git push -q origin HEAD:refs/heads/<BRANCH>` (never force; the explicit refspec also creates the branch on an empty remote). A rejection is classified by pure `classify_push(exit_ok, stderr)`:
   non-fast-forward / "fetch first" (another machine pushed after step 4) -> repeat from step 4, at most `PUSH_ATTEMPTS` (R1, R3: machines must
   converge, not loop forever). Any other refusal (protected branch, permission, hook declined, unknown) is a FAILURE: log, count for backoff, stop;
   no retry. Repeats merge against the DB already updated by the previous pass; merging identical rows is a no-op.
8. After a successful push, or when no commit was needed: record `last_synced_commit` = the pushed HEAD (or TIP) in the state file (temp + rename).
   No TIP and nothing to commit: record nothing.
9. Update state (last pull time, failure count, last access check). Release the lock (drop the `File`). No follow-up sync is spawned (R10).

Crash argument (R4): `last_synced_commit` is written only after the push. A crash anywhere (after step 5, before the push, mid-push) leaves it
older. The next cycle then reads OURS (already holding the applied MERGED and the live queue), the same or a newer THEIRS, and the older BASE.
Every id the crash left half-synced is either present on both sides (identical rows merge to themselves), added on one side (kept), or absent on
both (dropped); no id is deleted that was not deleted by one side; a queue group added before the crash is kept (added on ours). So the cycle
converges and repeating it changes nothing. Queue-versus-DB crash points: after the queue write and before the DB commit the DB is rolled back and
the queue holds a group whose values are all still in the DB or in THEIRS (harmless, deduped by key); after the DB commit the queue is already
on disk. At no point is a losing value in neither the DB nor the queue.
Every git call runs with `GIT_TERMINAL_PROMPT=0` and logs through `journal!`; a failure names the command and its stderr.

**`lessons resolve [--domain <d>]` (R9)** (subcommand of the same binary; code in `sync.rs`, SQL only through `store.rs`):
- Requires a TTY on stdin and stdout; otherwise it prints the queue as one JSON array and exits 0, so it never hangs a script.
- Locking (R9, R10): the clone lock is taken ONLY around each apply (the `store::update` plus the live-queue write), with `File::try_lock`, and released
  before `$EDITOR` opens, before waiting for the user's next choice, and before spawning the sync. Reading and showing the queue
  needs no lock (the live queue is replaced by rename). Under the lock the group is re-read. Lock held by a running sync at apply time -> no retry:
  it prints "sync in progress, try again", exits 0 and applies nothing, so the group stays queued and the choice is never lost (the user is asked
  again on the next `lessons resolve`).
- For each queued group it shows: lesson title, field, every version with its `updated_at`, the base value, and the DB's current value (which may equal none of
  the versions after a local edit; the next cycle adds it as a version). A group whose lesson no longer exists is cleared and logged.
- Choices per group: keep one version (any of them, the current one included), combine, edit in `$EDITOR` (opened on a temp file holding all
  versions), skip (group stays). Applied through the existing `store::update` with a `LessonPatch` of that one field. `update` bumps `updated_at` to now. When the field is `tags`,
  the current DB tags contain `needs-reword` and the chosen value lacks it, the token is kept (appended, space-separated) in the same patch.
  Keeping the current value is NOT a no-op: it still goes through `store::update` with the chosen value, so the choice is a local edit with a fresh
  `updated_at`. Accepted limit: `store::update` only bumps the row's `updated_at`, which changes the default-winner order of LATER conflicts, not the per-field
  merge result (values are compared, not times); a keep-current equal to BASE still yields to another machine's different resolution, both machines
  converge on one value and nothing is lost silently (flagged to @me).
- Combine writes one labelled block per version, `--- version of <updated_at> ---\n<value>` (versions ordered by `updated_at`, then value; a
  `None` value prints `(empty)`), into the field and adds `NEEDS_REWORD_TAG` to `tags`; it is then found with the existing `lessons list --tag needs-reword`.
  Tags are SPACE-separated (`store.rs` list matches `' ' || tags || ' '`; `main.rs` "Space-separated tags"): adding the tag appends `" needs-reword"`
  when absent (nothing when already there). For the `tags` field itself, combine is the union of the space-split lists, joined with single spaces
  (labelled blocks make no sense in a tag list); the tag is still added.
- After each applied choice the group is removed from the live queue (temp + rename). The resolution reaches other
  machines through the normal sync (live: the background sync is spawned after the lock is released; on-demand: the next throttled read pushes it). Crash recovery: a crash
  between the `update` and the queue removal leaves the group; a keep-one-version choice is then shown again and resolves as a no-op (the DB already
  holds that value). A crash after a combine's `update` leaves the group; the combined text matches no version, so the next cycle adds it as a version and the user can
  keep it on the next `lessons resolve`; the lesson is also found by its `needs-reword` tag (the field and the tag go in ONE `store::update` patch, so they land together).
- No `search`/`list` conflict notice in this plan (not requested; see Possible follow-ups). No new MCP tool.

**Commands (R1, R4, R9).** `lessons sync [--domain <d>]` and `lessons resolve [--domain <d>]` are the only new public commands. Export and import are folded
into sync; there is NO public `export`, `import` or `merge-jsonl`. `store.rs` gains `all_lessons(conn)` (reusing `LESSON_SELECT_COLUMNS`,
`lesson_from_row`) and `apply_merged(transaction, ours, merged)` which owns all SQL for the apply (it reuses the private `copy_into` for insert and
update, and `DELETE FROM lesson WHERE id = ?1`). `copy_into` stays private.

**Strategies (R3).**
- Reads (`search`, `list`, `show`, MCP `search_lessons`, the hook): when the last pull is older than `pull_every_minutes`, spawn
  `lessons sync --domain <d>` in the background, never inline. After a failure, the next attempt waits
  `min(base * 2^failures, BACKOFF_CAP_MINUTES)` ("with backoff"; the cap bounds the wait). Both take a passed-in clock.
- Writes (`add`, `update`, `hit`, `retire`, `move`, MCP `record_lesson`) under `live`: spawn the background
  sync (overlapping syncs of one session are stopped by the lock). Under `on-demand`: nothing; the next throttled read syncs and pushes it.
- Spawn (R3): `std::env::current_exe()`, stdin/stdout/stderr null; on Unix `CommandExt::process_group(0)` so a signal sent to a hook's or
  MCP client's process group does not kill a push. In the long-lived MCP server the child is reaped in a detached thread (`child.wait()`), so no
  zombies; the short-lived CLI and hook do not wait. A spawn failure is logged and ignored: the write itself never fails because of sync.

**Ownership (R1-R6, R9).** `config.rs`: parsing, remote normalising, the same-remote warning and the different-key error. `store.rs`: all SQL
(`all_lessons`, `apply_merged`; `update` reused by resolve). `sync.rs`: `merge_lessons`, `merge_queue`, `classify_push`, git orchestration,
lock/state files, guards, spawning, the resolve loop. `main.rs`: the `sync` and `resolve` commands and the trigger calls
(`hook.rs`, `mcp.rs` call the same trigger functions).

**.gitignore (R8).** The code repo's `.gitignore` gains `*.jsonl` (the JSON lines, conflict queues included, are the private DB as text), beside
the existing `*.db`, `*.db-wal`, `*.db-shm`, `*.db-journal`, `*.sqlite*` and `.lessons/`. `tests/gitignore.rs` gains `work.jsonl`, `personal.jsonl`,
`shared.jsonl`, `shared.conflicts.jsonl` and `nested/dir/shared.jsonl` in `private_paths`. No file tracked today matches `*.jsonl`
(`git ls-files | grep jsonl` is empty). Sync clones live under `$LESSONS_HOME/sync/`, outside the code repo.
